### How the key can be rotated
Every encrypted value records the ID of the key that encrypted it (`enc:v1:<keyId>:…`), so old and new keys can coexist:
1. Generate a new 32-byte key and set it as `HEALTH_DATA_KEY` with a new `HEALTH_DATA_KEY_ID` (e.g. `k2`). Move the old key to `HEALTH_DATA_OLD_KEYS=k1=<old key>`, and restart. New saves use k2; old values still decrypt with k1.
2. Run `npm run db:reencrypt-health`. It decrypts every k1 value and re-encrypts it with k2, in one transaction (all or nothing).
3. Check that nothing uses k1 any more (the script reports `rotated: 0` on a second run), then remove `HEALTH_DATA_OLD_KEYS` and destroy the old key.

In production, the key should live in a secrets manager or KMS rather than a `.env` file. Envelope encryption (a KMS-held master key wrapping a data key) would let the master key rotate without re-encrypting the data.

- **Wrong key** (a different random key) → integrity error, not garbage.
- **Rotation:**
  - new key k2 with old key k1 → reads OK
  - `reencrypt-health` → `rotated: 30`; table now all `k2`
  - k2 alone → reads OK; k1 alone → integrity error
  - a second run → `rotated: 0` (safe to re-run)
  - a plaintext legacy value → `encrypted_plaintext: 1`

### c) Limitations and assumptions
- **Only the 5 named text fields are encrypted, as specified.** The yes/no health answers (`has_heart_condition`, `has_chest_pain`, `is_pregnant`, `smoker`, …) and `fitness_goals` / `activity_level` are **still plaintext**, and they're also health data under GDPR. Encrypting them would need a column type change.
- **The key sits in `.env.local` on each machine,** in the same place as the database password. Someone who gets both can decrypt. A secrets manager or KMS would separate them.
- **The whole team must use the same `HEALTH_DATA_KEY`**, because the database is shared. A teammate with a different key gets integrity errors. Share it privately (not in GitHub or chat logs).
- **Data in use is decrypted in server memory and sent to authorised users over HTTP.** That's local development; production needs HTTPS. This control protects data at rest only.
- **Ciphertext length reveals the approximate length** of the text.
- **Encrypted fields can't be searched or sorted in SQL.** Nothing in the app needs that today.
- **Supabase backups and database logs** made before encryption still contain plaintext. They aren't covered.
- **An integrity error blocks the member from seeing their own questionnaire** until an admin fixes the data. That's deliberate (fail closed).
