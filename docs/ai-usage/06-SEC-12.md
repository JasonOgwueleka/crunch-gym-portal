## Prompt (verbatim)

```text
Implement security requirement SEC-12: Tamper-evident audit log.

User story: As an admin, I want the audit log protected so that any change to
it can be detected.

Acceptance criteria:
1. Security events are logged: login success, login failure, lockout, logout,
   access denied (403), role change, refund, password change/reset, file
   upload rejected.
2. Each new audit log entry stores a SHA-256 hash of (its own content + the
   previous entry's hash), forming a hash chain.
3. An admin-only endpoint GET /api/admin/audit-logs/verify checks the whole
   chain and reports whether it is intact, and the ID of the first broken
   entry if not.
4. Audit log rows cannot be updated or deleted through the app (enforce with
   a database trigger in a migration).
5. No passwords, tokens or health data are ever written to the log.
6. Show the verify result on the admin audit log page.

Make sure two requests at the same time cannot break the chain.

Deleting a user must still work. Old audit rows must not be changed when a
user is deleted (keep actor_email in the row; the foreign key must not
modify audit rows).
```

### c) Limitations and assumptions
- **No secret key (plain SHA-256, as specified).** Someone with database-owner rights can switch the triggers off and rewrite a row *and every hash after it*, producing a chain that verifies. The chain only detects tampering by someone who doesn't recompute the rest. Stronger options, not implemented: an HMAC with a key held only by the app, or regularly exporting the latest hash somewhere the DB admin can't change.
- **Deleting the newest entries** (the tail of the chain) isn't detected, because nothing points to them yet. Exporting the head hash would solve this too.
- **TRUNCATE isn't blocked.** Row triggers don't fire on TRUNCATE, and the seed script relies on it. A DB admin could empty the whole table.
- **The triggers stop the app and normal SQL users.** They don't stop the database owner, who can disable them (shown in T-12c).
- **Redaction works on detail *key names*.** A sensitive value stored under an innocent key name (e.g. inside a free-text "notes" field) would not be redacted.
- **Every 403 is logged,** including harmless ones (e.g. a member opening an admin page), which adds volume.
- **Verify reads the whole table** each time, in batches of 1,000 — fine at this size.
- Re-running migrations is safe. The seed script empties and re-chains the log (uses TRUNCATE).
