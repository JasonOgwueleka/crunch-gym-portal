## Prompt (verbatim)

```text
Implement security requirement SEC-05: Session hardening.

User story: As a member, I want my session to be protected so that someone
can't hijack or reuse it.

Acceptance criteria:
1. The session ID is regenerated on successful login (prevent session
   fixation).
2. Idle timeout: a session with no activity for 15 minutes is invalid.
3. Absolute timeout: a session is invalid 8 hours after login, even if active.
4. Logout, password change and password reset destroy the session
   server-side. Password change and reset also destroy ALL other sessions
   for that user.
5. Cookie flags: HttpOnly, SameSite=Strict, and Secure when
   NODE_ENV=production.
6. After the session expires, the React app sends the user to the login page
   with a clear message.

Make the idle and absolute timeouts configurable through environment
variables (defaults 15 minutes and 8 hours) so they can be shortened for
testing or lengthened for automated scans.
```

### Verification run by the AI (to be independently repeated by the owner)
Test API instance with `SESSION_IDLE_TIMEOUT_MINUTES=1` and `SESSION_ABSOLUTE_TIMEOUT_MINUTES=2`:
- **Cookie:** `crunch.sid=…; Path=/; Expires=…; HttpOnly; SameSite=Strict`. With `NODE_ENV=production` behind HTTPS (`X-Forwarded-Proto: https`, `TRUST_PROXY=loopback`) it adds `Secure`.
- **Fixation:** logging in while holding an existing session ID issued a new ID. The old ID was deleted from the DB and returns 401.
- **Logout:** the session row was deleted, and replaying the old cookie → 401.
- **Two sessions for Leah, change password in one:** both → 401 (`sessions_ended: 3` in the audit log). The password was then restored.
- **Password reset:** the existing session → 401 after the reset.
- **Idle:** one request at +30 s, then nothing. At +95 s (65 s idle) → 401 `X-Session-Expired: idle`, `code: SESSION_EXPIRED`, with the message; row deleted.
- **Absolute:** a request every 20 s stayed 200 until +102 s; +122 s → 401 (over 2 min since login despite the activity).
- **Expired cookie on a public page (`/plans`)** → 200, served as a visitor.
- **Audit log:** `auth.session_expired` (idle and absolute), and `auth.change_password` / `auth.password_reset` with `sessions_ended`.
- **Regression through the app (:5173):** all 5 role logins and their main pages → 200; front desk → admin → 403. The client build succeeds.

### c) Limitations and assumptions
- **Production must use HTTPS.** With `NODE_ENV=production` over plain HTTP, the server sends no cookie, so login appears to work but the user isn't kept logged in. Behind an HTTPS reverse proxy, `TRUST_PROXY` must be set so Express knows the connection is secure.
- **Existing sessions from before SEC-05** have no timestamps and are treated as expired. Everyone gets logged out once after upgrading.
- **Idle expiry is detected on the next request.** There's no client-side timer, so an idle tab keeps showing the last page until the user clicks something; then they go to the login page.
- **Race:** a request already in progress from a session when it's deleted (e.g. during a password change) can re-save that session when it finishes, because the session store saves with an upsert. The window is one request long.
- **SameSite=Strict** means arriving at the app from an external link (e.g. an email) shows you as logged out on that first page load; clicking within the app works. Password-reset links don't need a session, so they're unaffected.
- **Admin role changes and deactivation** don't delete sessions, but loadUser re-reads the user on every request, so the new role or deactivation applies immediately.
- **Every authenticated request writes the session** (to update `lastActivityAt`). This is one small DB write per request, the same as the previous rolling-cookie behaviour.
