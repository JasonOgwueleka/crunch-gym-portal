## Prompt (verbatim)

```text
Implement security requirement SEC-10: Safe file uploads.

User story: As an admin, I want uploaded files checked so that nobody can
upload malware or scripts.

Acceptance criteria:
1. Certificates (/api/certifications) accept only PDF, JPG and PNG. Progress
   photos (/api/progress) accept only JPG and PNG.
2. The type is checked by the real file content (magic bytes), not the
   extension or the Content-Type sent by the client.
3. Max file size 5 MB.
4. Stored filenames are random and the extension is set from the detected
   type. The original filename is sanitised before being stored in the
   database.
5. Files are returned with Content-Disposition: attachment (inline for images
   only), the correct Content-Type, and X-Content-Type-Options: nosniff.
6. A rejected file is deleted from disk immediately, returns HTTP 400 with a
   clear message, and is written to the audit log.

Upload handling is in server/src/utils/uploads.js (multer).
```

### c) Limitations and assumptions
- **Magic bytes prove the start of the file, not that the whole file is harmless.** A real PNG or PDF can carry extra data (the polyglot above), and PDFs can contain JavaScript or malicious content. Mitigations here: images are served with `nosniff` and a sandbox CSP, and PDFs are forced to download. There's **no malware or antivirus scanning** and **no re-encoding** of images.
- **Image metadata (EXIF, e.g. GPS location) isn't stripped** from photos.
- **The sanitised name can lose information**: `../../evil<script>alert(1)</script>.pdf` became `script_.pdf`, because the `/` in `</script>` counts as a path separator. It's safe, just less readable.
- **Files uploaded before SEC-10** keep their stored type. If it's not on the allow-list, they're served as a download (`application/octet-stream`).
- **Certificates now download instead of opening in the browser tab** (attachment), as required.
- **The 5 MB limit is enforced per file**; there's no per-user storage quota.
