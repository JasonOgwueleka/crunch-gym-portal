## Prompt (verbatim)

```text
Implement security requirement SEC-01: Brute-force protection.

User story: As a member, I want repeated failed logins to be blocked so that
attackers can't guess my password.

Acceptance criteria:
1. After 5 failed login attempts for the same account within 15 minutes, that
   account is locked for 15 minutes, even if the correct password is then
   entered.
2. Rate limit per IP on POST /api/auth/login, /api/auth/register and
   /api/auth/forgot-password (max 10 requests per minute per IP). Return
   HTTP 429 when exceeded.
3. The login error message and response time must be the same whether the
   email exists or not (no user enumeration).
4. Lockouts and rate-limit hits are written to the audit log
   (server/src/utils/audit.js).
5. A successful login resets the failed-attempt counter.

Store lockout state in the database (not memory) so it survives a server
restart.
```

### c) Limitations and assumptions
- **Rate-limit counters are in memory.** They reset on restart and aren't shared between multiple server processes. The *lockout* is in the DB as required. A shared store (e.g. Redis) would be needed for multiple servers.
- **Behind the Vite proxy every browser appears as `::1`**, so locally all users share one rate-limit counter. When deployed behind a real reverse proxy, `TRUST_PROXY` must be set correctly, or everyone shares the proxy's counter.
- **Targeted lockout (denial of service):** anyone who knows a member's email can keep that account locked by sending 5 wrong passwords every 15 minutes. This trade-off is inherent to account lockout. Mitigations (CAPTCHA, unlock by email, admin unlock) aren't implemented.
- **`login_throttle` grows** with one row per distinct email tried (including made-up ones). Rows are deleted on successful login but not otherwise cleaned up.
- **Timing is equal to within network noise, not to the millisecond.** The locked path (≈100 ms) is faster than the password path (≈280 ms), but it's the same for real and fake emails.
- **Race window:** a correct-password request already in flight when the 5th failure lands can still succeed. This is the time-of-check vs time-of-use (TOCTOU) window, a few milliseconds wide.
- **Out of scope here:** registration still answers "already exists" (409) for a taken email, which is user enumeration via registration. Password reset doesn't clear a lockout. There's no admin unlock.
- **Deactivated accounts** still return a distinct 403, but only after the correct password is given.
