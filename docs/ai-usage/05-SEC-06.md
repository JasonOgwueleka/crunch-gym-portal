## Prompt (verbatim)

```text
Implement security requirement SEC-06: CSRF protection.

User story: As a member, I want my account protected from forged requests so
that a malicious website can't perform actions as me.

Acceptance criteria:
1. Every state-changing request (POST, PUT, PATCH, DELETE) under /api
   requires a valid CSRF token.
2. A missing or invalid token returns HTTP 403 and the action is not
   performed.
3. The token is bound to the user's session and changes when the session is
   regenerated.
4. GET requests never change data (check all routes and list any that do).
5. The React app (client/src/lib/api.js) fetches the token and sends it
   automatically in a header, so all existing forms still work, including
   file uploads (multipart).
6. CSRF failures are written to the audit log.

Use the synchronizer token pattern or double-submit cookie. Tell me which and
why. Do not use the deprecated csurf package.
```

### Pattern chosen: synchronizer token (not double-submit cookie)
The app already keeps a server-side session in Postgres for every logged-in user (SEC-05), so the token can be stored there and never exposed in a cookie.
- **Bound to the session:** it changes automatically on login and logout. A double-submit cookie only checks that the cookie and header match, so it's weaker if an attacker can plant a cookie (for example from a sibling subdomain or over plain HTTP).
- **Can't be read by other origins:** it isn't stored in a cookie or in localStorage. Other origins can't read `GET /api/auth/csrf-token`, because CORS isn't enabled.
- **No extra library:** the deprecated `csurf` package wasn't used.

### c) Limitations and assumptions
- **Anonymous visitors get a session** (and a row in `user_sessions`) the first time the app needs a token, i.e. just before login or registration. Simply browsing plans or the timetable doesn't create one.
- **Automatic retry:** the client retries once with a new token after a 403 `CSRF_INVALID`, so a legitimate user whose session changed doesn't see an error. An attacker can't use this, because they can't read the token.
- **CSRF tokens don't protect against XSS.** Script running on our own origin could read the token. XSS defences (output encoding, CSP) are separate controls.
- **No Origin/Referer allow-list check** was added as a second layer; only the token is enforced. Origin is recorded in the audit log.
- **Automated scanners (ZAP, Strix) will get 403** on most POSTs unless they send the header, e.g. with a ZAP Replacer rule. That's the control working, but it reduces scan coverage.
- **The `/admin/reports/:name.csv` GET still writes an audit entry** (logging the export). It's a log of a read, not a change to app data.

### Note found during SEC-06 (affects SEC-05, not changed here)
While reviewing GET routes, the AI found that the React layout polls `GET /api/messages/unread-count` **every 30 seconds** for members and trainers (and the Messages page reloads the thread every 15 s). These background requests count as activity, so **a member's or trainer's session never reaches the 15-minute idle timeout while a tab is open**. Claim SEC-05-C2 is therefore only partly true: the AI's own SEC-05 test used direct HTTP requests, not a browser, and missed this.
